# PROJECT_IDEA — Telegram-бот для ведения пациентов

> Рабочее название: **«Доктор Кто»** (DoctorWho Bot).
> Статус документа: черновик v0.1 (2026-11-02). Пункты с пометкой **[?]** — допущения, требуют подтверждения.

---

## 1. Суть проекта

Telegram-бот — персональный ассистент врача для ведения пациентов. Врач прямо в мессенджере
заводит карточки пациентов, записывает приёмы, назначения и заметки, ставит напоминания
о контрольных визитах и быстро находит нужную информацию — без громоздких МИС и бумажных журналов.

### Проблема
- Врачи частной практики, узкие специалисты и консультанты часто ведут пациентов
  в блокнотах, Excel, заметках телефона и переписках — информация разрознена.
- Полноценные медицинские информационные системы (МИС) дорогие, сложные и привязаны к клинике.
- Легко забыть про контрольный приём, повторный анализ или окончание курса лечения.

### Решение
- Всё в одном месте — в Telegram, который у врача и так всегда открыт.
- Быстрый ввод: короткие команды, кнопки, пошаговые диалоги (в перспективе — голосовые заметки).
- Автоматические напоминания врачу (и, опционально, пациенту).

### Целевая аудитория
| Сегмент | Описание |
|---|---|
| Основной | Частнопрактикующие врачи, узкие специалисты (кардиолог, эндокринолог, психотерапевт, стоматолог и т.п.) |
| Дополнительный | Небольшие клиники / кабинеты (2–10 врачей) |
| Перспектива | Пациенты — как получатели напоминаний и инструкций |

## 2. Роли пользователей

| Роль | Возможности |
|---|---|
| **Врач** (основная) | Полный доступ к своим пациентам, приёмам, заметкам, напоминаниям |
| **Пациент** [?] (этап 3) | Получает напоминания, подтверждает визит, видит свои назначения |
| **Администратор** | Управление пользователями бота, статистика, модерация доступа |

Принцип изоляции: **врач видит только своих пациентов**. Любой запрос к данным фильтруется по `doctor_id`.

## 3. Функциональные требования

### 3.1 MVP (этап 1)
1. **Регистрация врача**: `/start` → ФИО, специализация, часовой пояс, согласие с политикой обработки данных.
2. **Пациенты (CRUD)**:
   - добавить пациента (ФИО, дата рождения, пол, телефон, примечание);
   - список пациентов с пагинацией (inline-кнопки);
   - поиск по ФИО / телефону;
   - карточка пациента: данные + последние приёмы + активные назначения;
   - редактирование и архивирование (мягкое удаление).
3. **Приёмы / визиты**:
   - создать запись о приёме: дата, жалобы, диагноз (текст, опц. код МКБ-10), назначения, комментарий;
   - история приёмов пациента в хронологическом порядке.
4. **Заметки**: быстрые текстовые заметки к пациенту.
5. **Напоминания врачу**:
   - «напомнить о контроле пациента X через N дней / в дату»;
   - ежедневная утренняя сводка: приёмы и контроли на сегодня.
6. **Главное меню** на reply-клавиатуре + команды: `/start`, `/menu`, `/patients`, `/add`, `/search`, `/today`, `/help`.

### 3.1а Запрос владельца (реализовано)
- Приём спрашивает анамнез и объективный статус; типы приёма: первичный осмотр и дневниковая запись.
- Пользовательские шаблоны (например, «Острый аппендицит»): заполняют приём, поля правятся под пациента.
- Печать в Word: первичный осмотр, дневниковые записи, история болезни.
- Результаты обследований (текст, фото, PDF) и их разбор ИИ.
- Вопросы к ИИ по пациенту с учётом его записей и без привязки к пациенту.

### 3.2 Этап 2
- Расписание / календарь приёмов (слоты, запись на время).
- Вложения: фото, PDF анализов, сканы (хранение файлов вне Telegram или по `file_id`).
- Шаблоны назначений и осмотров для специализации.
- Теги/группы пациентов (например, «диабет», «после операции»).
- Экспорт карточки пациента / выписки в PDF или DOCX.
- Экспорт всей базы врача (CSV/XLSX).

### 3.3 Этап 3
- Доступ пациента: привязка по одноразовому коду-приглашению, напоминания пациенту о визите и приёме лекарств, подтверждение/отмена визита.
- Голосовые заметки → расшифровка в текст (speech-to-text) [?].
- Голосовой ввод и структурирование свободного текста приёма в поля карточки [?].
- Мультиврачебный режим для клиник (общие пациенты, роли, передача пациента).
- Web-панель / Telegram Mini App для удобного просмотра больших карточек.

### 3.4 Вне рамок проекта
- Самостоятельные решения бота: ИИ подсказывает врачу, решение всегда за врачом. Пациентам советы не отправляются.
- Интеграция с ЕГИСЗ / государственными МИС (не на ранних этапах).
- Онлайн-оплата (возможно позже).

## 4. Пользовательские сценарии (примеры)

**Добавление пациента**
```
Врач: ➕ Новый пациент
Бот:  Введите ФИО пациента
Врач: Иванов Иван Иванович
Бот:  Дата рождения (ДД.ММ.ГГГГ)
Врач: 12.03.1975
Бот:  Телефон (или «пропустить»)
...
Бот:  ✅ Пациент добавлен. [Открыть карточку] [Добавить приём]
```

**Запись приёма**: карточка → «Добавить приём» → жалобы → диагноз → назначения →
«Напомнить о контроле?» [через 7 дн] [через 14 дн] [через 30 дн] [своя дата] [нет].

**Утренняя сводка (08:00 по часовому поясу врача)**
```
📅 Сегодня, 3 ноября:
• Контроль: Иванов И.И. (гипертензия) — назначен 20.10
• Контроль: Петрова А.С. — повторный ОАК
```

## 6. Архитектура

```
Telegram ⇄ aiogram Dispatcher
              │
         middlewares (DB-сессия, авторизация врача, логирование, throttling)
              │
         handlers/ (routers по фичам: patients, visits, notes, reminders, admin)
              │
         services/ (бизнес-логика, без зависимостей от aiogram)
              │
         repositories/ (доступ к БД через SQLAlchemy)
              │
         PostgreSQL        Redis (FSM)        APScheduler (jobs)
```

Принципы:
- Handlers тонкие: разбор ввода → вызов сервиса → ответ. Логика — в `services/`.
- Сервисы не знают про Telegram — легко тестировать и переиспользовать (например, для Mini App).
- Все тексты бота — в отдельном модуле (`texts.py` / локализация), не хардкодить в хендлерах.
- Клавиатуры — в `keyboards/`, callback-данные через `CallbackData`-фабрики aiogram.

### Предлагаемая структура
```
bot/
  __main__.py          # точка входа
  config.py            # настройки (pydantic-settings)
  db/
    models.py          # SQLAlchemy-модели
    session.py
    repositories/
  services/
  handlers/
    common.py  patients.py  visits.py  notes.py  reminders.py  admin.py
  keyboards/
  states/              # FSM StatesGroup
  middlewares/
  scheduler/
  texts.py
  utils/
migrations/            # Alembic
tests/
docker-compose.yml
Dockerfile
.env.example
```

## 7. Модель данных (черновик)

| Таблица | Ключевые поля |
|---|---|
| `doctors` | id, telegram_id (unique), full_name, specialty, timezone, consent_at, is_active, created_at |
| `patients` | id, doctor_id → doctors, full_name*, birth_date*, sex, phone*, notes*, is_archived, created_at, updated_at |
| `visits` | id, patient_id, doctor_id, visit_date, complaints*, diagnosis*, icd10_code, prescriptions*, comment*, created_at |
| `notes` | id, patient_id, doctor_id, text*, created_at |
| `reminders` | id, doctor_id, patient_id (nullable), remind_at (UTC), text, status (pending/sent/cancelled), created_at |
| `attachments` (этап 2) | id, patient_id, visit_id, tg_file_id / storage_path, mime, created_at |
| `audit_log` | id, doctor_id, action, entity, entity_id, created_at |

`*` — поля с персональными/медицинскими данными, хранятся в зашифрованном виде.
Поиск по зашифрованному ФИО — через отдельный нормализованный хэш/индекс [?].
Все даты в БД — в UTC; отображение — в часовом поясе врача.

## 8. Безопасность и законодательство

Медицинские данные — **особо чувствительная категория персональных данных** практически в любой
юрисдикции (например, GDPR ст. 9) и предмет врачебной тайны. Это ключевое ограничение проекта.
Владелец проекта не из РФ — требования 152-ФЗ о локализации не применяются.

Обязательные меры:
- Доступ только зарегистрированным врачам (whitelist / приглашение от администратора на старте).
- Строгая изоляция данных по `doctor_id` на уровне репозиториев.
- Шифрование чувствительных полей в БД; ключ — только в переменных окружения.
- Секреты (`BOT_TOKEN`, `DB_URL`, `ENCRYPTION_KEY`) — только в `.env`, файл в `.gitignore`.
- Никаких ПДн в логах, сообщениях об ошибках и аналитике.
- Согласие на обработку ПДн при регистрации; политика конфиденциальности.
- Регион хранения данных (Supabase) — ближе к врачам и с учётом законов их страны [?].
- Минимизация данных: предпочитать инициалы/псевдонимы, если врачу достаточно.
- Бэкапы БД (зашифрованные), возможность полного удаления данных врача по запросу.
- Учитывать, что сообщения в Telegram хранятся на его серверах: не дублировать в чат больше данных,
  чем нужно; опция автоудаления сообщений с карточкой [?].
- Rate limiting / throttling, валидация всего пользовательского ввода.

## 9. Нефункциональные требования
- Ответ бота на действие — < 1 с в обычном режиме.
- Устойчивость к перезапуску: напоминания хранятся в БД, а не только в памяти планировщика.
- Нагрузка на старте: до ~100 врачей, до ~10 000 пациентов суммарно.
- Интерфейс полностью на русском языке; понятные кнопки, минимум ручного ввода команд.
- Покрытие тестами сервисного слоя ≥ 70 %.
